## 先说清楚一件事：这是重建后重跑的

原始那份验证脚本没有留下来（这也是本书 2026 年 10 月版一度只能写「脚本与输出未随书保留」的原因）。本目录里的脚本是**按书里印出来的表重建**的：

| 模型从哪里来 | 书里位置 |
|---|---|
| 管理 FSM：4 状态 × 6 事件 = 24 格，其中 accepted 16、显式拒绝 8 | 表 30 完整转移矩阵 |
| 横切 FSM：7 状态 × 6 事件 = 42 格 | 图 18（主链 + 升级分支）+ 表 32（同一事件在不同状态下的处理） |
| 四类属性：完备性、安全性、活跃性、不变量 | 表 31 |
| 那条 11 步轨迹 | 17.4 节 |

**2026-10-18 重跑的结果与书里印的数字一致**：24 / 24、42 / 42、19 / 19、5000 条 × 20 步 0 例未定义转移、幂等压缩 11 → 8。也就是说，书里那些数字现在可以被任何人重新算一遍，而不是只能被相信。

它不是原件，是复算。这两件事在证据强度上不同，所以不合并表述。

## 跑

```bash
python fsm_verify.py                       # 19 项检查 + 两个 FSM 各 5000 条 × 20 步
python fsm_verify.py --n 20000             # 加大压力
python fsm_verify.py --out run.txt         # 写文件，与 fsm_verify_output.txt diff
```

只用标准库，不联网，两秒左右。**输出是确定的**：随机种子固定为 20261018，同一台机器（甚至同一 Python 小版本）跑两遍，输出逐字节相同——所以 `diff` 能当验证手段用。

`fsm_verify_output.txt` 是随书存档的那一次输出。

## 19 项检查是什么

**管理 FSM（9 项）**

| # | 属性 | 检查什么 |
|---|------|---------|
| 01 | 完备性 | 24 个 (状态, 事件) 组合全有定义 |
| 02 | — | 每个目标要么是已声明状态，要么是 REJECT（防手误） |
| 03 | 安全性 | 不存在 RED → GREEN 的捷径（对应 16.5 节那个被验证器抓出来的设计错误） |
| 04 | 安全性 | CLOSED 为吸收态：除「项目结束」自环外全部 REJECT |
| 05 | 活跃性 | GREEN → CLOSED 可达 |
| 06 | 活跃性 | 四个状态都能到达 CLOSED（无死状态） |
| 07 | 不变量 | 从别的状态进入 RED，触发事件只有 escalation / member_resign |
| 08 | 不变量 | 除 CLOSED 外，核心离职一律进 RED（16.2 那条「任意状态」规则的例外被显式测出来） |
| 09 | 随机压力 | 5000 条 × 20 步，未定义转移 0 例 |

**横切 FSM（10 项）**

| # | 属性 | 检查什么 |
|---|------|---------|
| 10 | 完备性 | 42 格全有定义 |
| 11 | — | 目标合法 |
| 12 | 安全性 | CLOSED 之后五个业务事件全部 REJECT |
| 13 | 活跃性 | IDLE → CLOSED 可达 |
| 14 | 活跃性 | 七个状态都能到达 CLOSED |
| 15 | 不变量 | 进入 ESCALATED 的事件只有 escalate |
| 16 | 阶段内幂等 | 五处自环：detect@DETECTED、contain@CONTAINED、escalate@ESCALATED、recover@RECOVERED、review@REVIEWED |
| 17 | 阶段外拒绝 | contain 在 IDLE / RECOVERED / REVIEWED / CLOSED 四处全 REJECT |
| 18 | 幂等压缩 | 11 步 → 8 步，且折掉的正好是 CONTAINED、RECOVERED、REVIEWED 三处重复 |

## 重跑时发现的一处书内冲突（已改）

表 32 第一行原写「DETECTED 收到 contain → REJECT（还没检测完就想处置）」。但图 18 的主链是 DETECTED → CONTAINED，那条箭头必须有一个事件触发，而能触发它的就是 contain——两者不可能同时成立。

按图 18 与 17.4 那条真实轨迹（第 2 步就是 DETECTED → CONTAINED）实现，并把这处记为书里的一格笔误：**表 32 第一行应为「CONTAINED（进入处置）」**，理由也不是「跳步」，而是「阶段推进」。阶段外拒绝的那几格（IDLE / 后面几态 / CLOSED）不受影响，17.3 节那句论证改成在 IDLE 上举例，逻辑更干净。书已在本次修订里改了这一格与那一句。

## 这个验证证明了什么、没证明什么

**证明了**：这两个 FSM 的转移矩阵在本目录的 19 条断言下是完备、安全、活跃、守住不变量的；11 步压缩到 8 步是这条规则算出来的，不是画出来的。

**没证明**：书里第 19 章 TCP 的那 13 项属性、第 21 章 Agent 契约里的那部分——它们有相当一部分仍是设计目标，没有对应的运行记录，本书也一直这么标注。FSM 只能验证已经建进模型里的属性，没建进去的它不会替你想到（16.9、附录 C 的 L3）。
